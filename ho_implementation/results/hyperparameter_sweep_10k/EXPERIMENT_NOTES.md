# HO 10k Hyperparameter Sweep Notes

## What was run

The sweep script, `ho_implementation/run_ho_hyperparameter_sweep.py`, uses the same trace and split as the GA, PSO, SFO, DSOA, and ABC 10k sweeps:

| Split | Request indices (1-based, inclusive) | Requests |
| --- | ---: | ---: |
| Training | 1–10,000 | 10,000 |
| Validation | 10,001–50,000 | 40,000 |
| Holdout | 50,001–90,000 | 40,000 |

The sweep evaluates `Dataset/cluster07(00).csv` after the same preprocessing pipeline used elsewhere in the project: high-priority ratio 30%, seed 42, cache size fixed to 10% of the training-block unique-object catalog, 20% DRAM / 80% SSD split, and one deterministic validation-selection policy. Each configuration uses 30 hippos, 25 iterations, and seed 42. The best configuration is selected on validation score only and is evaluated once on the untouched holdout block.

This is one seeded run, not an average across repeated seeds.

The objective weights are fixed to match the other algorithms: total CHR 0.40,
HPC CHR 0.35, normalized penalty 0.15, and normalized latency 0.10. The fitness formula is
`0.40 * total_CHR + 0.35 * HPC_CHR - 0.15 * normalized_penalty - 0.10 * normalized_latency`.

`levy_10` was the selected configuration on validation. It uses `p_defense=0.50`
and `beta_levy=1.00`. Its untouched 40,000-request holdout results were 67.62%
Total CHR, 69.61% HPC CHR, 66.75% LPC CHR, 312,470 total penalty, and 34.41 ms
average retrieval time.

Per-iteration best/average fitness, CHR, phase counts, and elapsed time are saved in
[`training_histories.json`](./training_histories.json). Full per-configuration
validation metrics, the selected holdout result, and runtime durations are recorded in
[`final_results.json`](./final_results.json). The progress checkpoint is
[`sweep_progress.json`](./sweep_progress.json).

## Simulated cache and storage model

These are simulator parameters, not measurements of physical machine hardware. They match the GA/PSO/SFO/DSOA/ABC sweep protocol:

| Modeled resource | Value | Basis |
| --- | ---: | --- |
| Unique-object catalog in training block | 6,135,728 bytes | Sum of unique training-object sizes |
| Total cache capacity | 613,572 bytes | 10% of the training catalog |
| DRAM cache tier | 122,714 bytes | 20% of total cache, integer-truncated |
| SSD cache tier | 490,857 bytes | 80% of total cache, integer-truncated |
| DRAM latency | 100 ns | Simulator constant |
| DRAM read bandwidth | 40 GB/s | Simulator constant |
| DRAM write bandwidth | 20 GB/s | Simulator constant |
| SSD latency | 10 µs | Simulator constant |
| SSD read bandwidth | 2 GB/s | `ssd_throughput_gb=2.0` |
| SSD write bandwidth | 1 GB/s | Half the configured SSD read throughput |
| Slot size | 1,781 bytes | Mean object size in the preprocessed trace |
| Upstream response time | Synthetic 10–200 ms per key | Deterministically generated by the trace preprocessor |

The independent integer truncation of the DRAM and SSD limits makes their sum
one byte smaller than the total cache limit. The SSD capacity above is the
simulated SSD cache tier, not the size of a physical SSD in the host machine.

## Reproducibility

From the repository root, run:

```bash
python -m ho_implementation.run_ho_hyperparameter_sweep
```

If the run is interrupted after at least one configuration finishes, resume from
its saved checkpoint with:

```bash
python -m ho_implementation.run_ho_hyperparameter_sweep --resume
```

Runtime observations can vary with system load. The search uses the recorded seed,
while the simulator's cache capacities, preprocessing, split policy, and objective
weights remain fixed across the sweep.
