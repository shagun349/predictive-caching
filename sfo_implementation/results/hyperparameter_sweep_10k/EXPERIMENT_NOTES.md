# SFO 10k Hyperparameter Sweep Notes

## What was run

The sweep script, `sfo_implementation/run_sfo_hyperparameter_sweep.py`, uses
the same trace and split as the PSO 10k sweep:

| Split | Request indices (1-based, inclusive) | Requests |
| --- | ---: | ---: |
| Training | 1–10,000 | 10,000 |
| Validation | 10,001–50,000 | 40,000 |
| Holdout | 50,001–90,000 | 40,000 |

Both sweeps use `Dataset/cluster07(00).csv`, the same deterministic trace
preprocessing (priority ratio 30%, seed 42), cache sizing (10% of the unique
training catalog), 20% DRAM / 80% SSD split, and validation selection formula.
Each SFO configuration uses 30 fish, 25 iterations, and seed 42. The seeded
QM-ARC-style, LRU, and LFU starting candidates are retained, as in the
existing SFO experiment.
The best configuration is selected on validation score only; the holdout block
is evaluated once after selection and is not used to tune settings. Results are
single seeded runs, not averages across repeated seeds.

The objective weights are held fixed to match the PSO sweep: total CHR 0.40,
HPC CHR 0.35, normalized penalty 0.15, and normalized latency 0.10. The fitness
formula is
`0.40 * total_CHR + 0.35 * HPC_CHR - 0.15 * normalized_penalty - 0.10 * normalized_latency`.

## SFO settings compared

`alpha` controls gathering toward the global best, `ts` is the number of
non-improving iterations before stagnation dispersal, and `pf` is the
per-dimension disturbance probability. The baseline uses the existing SFO
defaults (`alpha=0.3`, `ts=5`, `pf=0.4`). Other configurations vary one setting
or combine settings while keeping the search budget unchanged.

| Configuration | `alpha` | `ts` | `pf` | Best training fitness | Validation score | Training time (s) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| baseline | 0.3 | 5 | 0.4 | 0.444370 | 0.451520 | 308.1 |
| gathering_02 | 0.2 | 5 | 0.4 | 0.444862 | 0.452141 | 353.3 |
| gathering_04 | 0.4 | 5 | 0.4 | 0.444465 | 0.450474 | 341.4 |
| stagnation_03 | 0.3 | 3 | 0.4 | 0.444370 | 0.451370 | 169.0 |
| stagnation_07 | 0.3 | 7 | 0.4 | 0.444370 | 0.451427 | 209.6 |
| disturbance_02 | 0.3 | 5 | 0.2 | 0.444115 | 0.449796 | 355.2 |
| disturbance_06 | 0.3 | 5 | 0.6 | 0.445238 | **0.452406** | 343.3 |
| exploration_low | 0.2 | 3 | 0.2 | 0.445227 | 0.451109 | 361.7 |
| exploration_high | 0.4 | 7 | 0.6 | 0.444859 | 0.452134 | 239.2 |
| balanced_04_05_06 | 0.4 | 5 | 0.6 | 0.444859 | 0.451994 | 307.6 |

`disturbance_06` won on validation, using `alpha=0.3`, `ts=5`, and `pf=0.6`.
Its untouched 40,000-request holdout results were 66.99% total CHR, 70.11% HPC
CHR, 65.61% LPC CHR, 311,155 total penalty, and 0.03490 seconds average
retrieval time.

Per-iteration best/average fitness, CHR, stagnation count, and elapsed time are
saved in [`training_histories.json`](./training_histories.json). Full
validation metrics for each configuration, selected holdout metrics, and
runtime durations are recorded in [`final_results.json`](./final_results.json).
The progress checkpoint is [`sweep_progress.json`](./sweep_progress.json).

## Simulated cache and storage model

These are simulator parameters, not cache hardware installed in the computer.
They match the PSO sweep:

| Modeled resource | Value | Basis |
| --- | ---: | --- |
| Unique-object catalog in training block | 6,135,728 bytes | Sum of unique training-object sizes |
| Total cache capacity | 613,572 bytes | 10% of the training catalog |
| DRAM cache tier | 122,714 bytes | 20% of total cache, integer-truncated |
| SSD cache tier | 490,857 bytes | 80% of total cache, integer-truncated |
| DRAM latency | 100 ns | Simulator constant |
| DRAM read bandwidth | 40 GB/s | Simulator constant |
| DRAM write bandwidth | 20 GB/s | Simulator constant |
| SSD latency | 10 µs | Simulator constant |
| SSD read bandwidth | 2 GB/s | Configured simulator throughput |
| SSD write bandwidth | 1 GB/s | Half the configured SSD read throughput |
| Slot size | Saved in `final_results.json` | Mean preprocessed object size |
| Upstream response time | Synthetic 10–200 ms per key | Deterministically generated by the trace preprocessor |

The independent integer truncation of the DRAM and SSD limits makes their sum
one byte less than the total cache limit. The simulated SSD tier size is not
the capacity of the physical SSD.

## Reproducibility

From the repository root, run:

```bash
python -m sfo_implementation.run_sfo_hyperparameter_sweep
```

If a run is interrupted after at least one configuration finishes, resume from
the saved checkpoint with:

```bash
python -m sfo_implementation.run_sfo_hyperparameter_sweep --resume
```

Runtime observations can vary with system load. The training search itself
uses the recorded seed, while the simulator's cache capacities, trace
preprocessing, objective, and train/validation/holdout splits are held fixed.
